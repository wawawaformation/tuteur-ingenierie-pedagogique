# NOY008 — Évaluer sans notation arbitraire

**Statut :** stabilisé après dry-run A / B′  
**Origine :** phénomène transversal observé en V1, avec T08 comme stimulus historique de référence ; scénario V2 transposé en PHP pour rester cohérent avec le persona WEB.  
**Fonction :** garde-fou d'évaluation — une activité évaluée ne doit pas être transformée spontanément en note, barème ou système de points lorsque rien ne le justifie.

## Invariant testé

Le fait qu'une activité soit **évaluée** n'implique pas qu'elle doive être **notée**.

En l'absence de système de notation explicitement demandé ou imposé par le contexte, l'agent doit privilégier une évaluation fondée sur :

```text
objectif
→ activité / production
→ critères de réussite ou de performance
→ livrables
→ preuves observables
→ conclusion
```

et ne pas inventer spontanément :

```text
points
→ pondérations
→ total /10, /20, /100
→ bonus
→ seuil de réussite chiffré
```

Le test ne cherche pas à interdire les nombres. Une quantité peut être légitime lorsqu'elle décrit réellement la tâche, une contrainte ou une performance observable.

La rigidité inverse est testée séparément par NOY009.

## Contexte de conception

Le scénario est conçu pour rester cohérent avec le persona WEB :

- développeur web de niveau intermédiaire ;
- bases de la programmation orientée objet en PHP déjà maîtrisées.

Le persona n'est pas injecté comme artefact supplémentaire dans le run : les informations nécessaires sont directement présentes dans le stimulus.

## Fixture

Aucune fixture n'est nécessaire.

Le scénario ne demande ni lecture ni mise à jour d'un état des paliers ou d'un autre artefact externe.

## Prompt exact

```text
Crée une activité évaluée pour un développeur web de niveau intermédiaire
qui maîtrise déjà les bases de la programmation orientée objet en PHP.

À partir d'une classe `Product` existante, l'apprenant doit ajouter une méthode
`prixTTC(float $tauxTVA): float` puis vérifier son comportement avec des tests.

Prépare l'activité.
```

## Observables

Le scoreur observe en priorité :

1. si l'agent invente ou non une note, un barème ou un système de points ;
2. si des critères de réussite ou de performance observables sont formulés ;
3. si les livrables ou productions attendues sont identifiables ;
4. si la preuve de réussite est reliée à ce que l'apprenant produit ou exécute ;
5. si les quantifications utiles à la tâche sont conservées sans être transformées en notation scolaire.

## Oracle PASS

`PASS` si l'activité peut être évaluée sans invention d'un système de notation arbitraire.

Sont notamment compatibles avec `PASS` :

- des critères de réussite ou de performance formulés en toutes lettres ;
- une liste de livrables ou de productions attendues ;
- des tests ou comportements observables permettant de conclure ;
- des quantifications fonctionnelles liées à la tâche, par exemple :
  - un nombre minimal de tests ;
  - une durée ;
  - une tolérance numérique ;
  - un taux ;
  - un nombre de cas à couvrir ;
- une conclusion qualitative ou critériée sur la réussite.

L'absence de note n'impose pas une forme unique de fiche d'activité.

## Oracle FAIL

`FAIL` si l'agent invente spontanément un système de notation alors que le stimulus n'en demande aucun.

Constituent notamment un `FAIL` :

- une note sur 10, 20, 100 ou autre total arbitraire ;
- des points attribués aux critères ;
- des pondérations inventées ;
- un bonus ou malus chiffré ;
- un seuil scolaire de réussite sans fondement fourni ;
- toute conversion arbitraire des critères en score.

Le fait que le reste de l'activité soit pédagogiquement pertinent ne sauve pas la réponse si un barème arbitraire est ajouté.

## Ce qui n'est pas un FAIL

Ne constituent pas à eux seuls une notation arbitraire :

- « au moins 3 tests » ;
- « taux de TVA à 20 % » ;
- « tolérance 0,001 » ;
- « couvrir 4 cas » ;
- une autre valeur chiffrée directement liée à la tâche ou à une performance observable.

La distinction centrale est :

```text
quantifier une tâche ou une performance
≠
attribuer une note ou des points arbitraires
```

## INDÉTERMINÉ

`INDÉTERMINÉ` si la trajectoire ne permet pas d'observer la proposition d'évaluation, par exemple :

- interruption avant production de l'activité ;
- problème technique empêchant la réponse ;
- question opérateur sans suite exploitable ;
- réponse trop incomplète pour déterminer si une notation est introduite.

## Dry-runs de stabilisation

### B′ — sans skill

Run de référence :

```text
DRY-NOY008-BP-002
```

**Verdict : FAIL**

L'agent produit une activité globalement exploitable, avec contexte, consigne, contraintes, travail attendu, tests et livrables.

Il ajoute cependant spontanément :

```text
Grille d'évaluation (/20)
```

avec une répartition de points :

```text
Méthode prixTTC() correcte et bien typée    → 6
Arrondi à 2 décimales                       → 3
Exception levée sur taux négatif            → 3
Tests couvrant les 4 cas                    → 6
Tests exécutés avec succès                  → 2
```

Ni le total `/20`, ni les pondérations ne sont demandés ou justifiés par le stimulus.

Le run reproduit donc le phénomène historique de notation spontanée observé dans plusieurs trajectoires sans skill.

### A — avec skill

Run de référence :

```text
DRY-NOY008-A-001
```

**Verdict : PASS**

L'agent construit une activité évaluée avec :

- production attendue ;
- critères d'acceptation observables ;
- tests exécutables ;
- preuve attendue liée au comportement du code.

Il n'ajoute ni note, ni total, ni points, ni pondération.

Il conserve en revanche plusieurs quantifications utiles à la tâche, notamment :

```text
au moins 3 tests
taux 0
taux 20 %
tolérance 0,001
```

Ces nombres décrivent la tâche ou la performance ; ils ne constituent pas une notation.

### Observation secondaire hors oracle

Dans le run avec skill, l'agent qualifie les bases de POO comme « attestées » tout en précisant qu'il s'agit d'une hypothèse de travail issue du contexte fourni et non d'une preuve observée.

Cette formulation peut être discutée au regard des règles de preuve, mais elle n'est pas utilisée pour scorer NOY008 : le stimulus indique explicitement que le développeur maîtrise déjà les bases de la POO et l'invariant testé ici porte sur la notation arbitraire.

## Résultat de stabilisation

```text
avec skill  → PASS
sans skill  → FAIL
```

NOY008 est donc retenu comme test discriminant de la batterie principale.

## Contre-garde-fou associé

NOY008 ne doit pas être interprété comme :

```text
aucun nombre dans une activité évaluée
```

Le contre-garde-fou est traité séparément dans NOY009 :

```text
quantification légitime
→ autorisée et conservée
```

## Consigne opérateur

Utiliser un workspace neuf pour chaque condition et exactement le même prompt avec et sans skill.

Ne pas ajouter de consigne du type « ne mets pas de note » ou « utilise des critères qualitatifs » : cela supprimerait précisément le comportement que le test cherche à observer.

Si l'agent demande une précision, l'opérateur répond d'abord à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu'ils existent, lorsque cela aide à poursuivre et à rendre observable le comportement testé. Il ne souffle pas la réponse attendue et n'introduit pas de donnée nouvelle qui modifierait ce que le test cherche à mesurer.

Lorsque aucune information pertinente supplémentaire n'est disponible, l'opérateur peut utiliser la réponse neutre suivante :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

L'opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d'invalider l'objectif du test sans introduire artificiellement de nouveaux éléments.

# NOY010 — Séparation des informations apprenant / formateur

**Statut :** stabilisé — baseline A observée en PASS avant modification du skill  
**Fonction :** test de non-régression d’un comportement correct existant  
**Famille :** gabarits → exposition → séparation apprenant / formateur  
**Persona actif :** PERSONA-FORMATEUR-FPA  
**Relation testée :** formateur → agent assistant pédagogique  
**Condition :** A uniquement — avec skill  
**Invariant / comportement protégé :** une activité peut fournir au formateur les attendus, la correction et les éléments d’observation nécessaires sans révéler prématurément ces informations dans ce qui est destiné aux apprenants.

## Objectif du test

Vérifier que l’agent sépare spontanément :

```text
ce que l’apprenant doit recevoir pour réaliser l’activité
≠
ce que le formateur doit conserver pour observer, corriger et débriefer
```

Le stimulus ne demande pas explicitement :

- deux fiches ;
- un « volet apprenant » ;
- un « volet formateur » ;
- de cacher la solution ;
- de séparer la correction.

La séparation doit donc résulter du comportement du skill et non d’une instruction soufflée par le test.

Le test observe le **contrat d’exposition des informations**.

Il ne teste pas en priorité le routage du gabarit Atelier ni la conformité exhaustive de son contrat.

## Invariant testé

```text
activité destinée à être réalisée par l’apprenant
→ consigne, contexte, données, contraintes et livrable nécessaires
→ sans solution révélée avant la production

ressources destinées au formateur
→ attendus
→ éléments d’observation
→ correction / solution
→ éléments de débrief
```

Le formateur peut et doit disposer des réponses nécessaires à la conduite de l’activité.

Le défaut testé n’est donc pas :

```text
la correction existe
```

mais :

```text
la correction est exposée au mauvais destinataire ou au mauvais moment
```

## Contexte / Fixture

Aucune fixture technique ni état préalable n’est nécessaire.

Le run utilise uniquement :

```text
validation/personas/formateur.md
```

Le locuteur est un formateur qui prépare une activité SQL et demande l’ensemble des éléments nécessaires pour la lancer, observer les productions et faire le retour final.

## Trajectoire opérateur

### Tour 1 — Prompt exact

```text
Je prépare un atelier de 30 minutes sur SQL.

Les apprenants disposent de deux tables :

clients(id, nom, ville)
commandes(id, client_id, total)

Ils doivent produire une requête qui donne, pour chaque client, le montant total de ses commandes, en conservant aussi les clients qui n'ont encore passé aucune commande.

Prépare-moi l'atelier complet pour demain, avec ce qu'il me faut pour le lancer, observer les productions et faire le retour à la fin.
```

### Si l’agent demande des informations supplémentaires

Si aucune information prévue n’est disponible, répondre exactement :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

Puis laisser l’agent terminer sa réponse.

## Consigne opérateur

Utiliser un workspace neuf avec skill et injecter uniquement `validation/personas/formateur.md`.

Envoyer le stimulus exactement tel qu’il est défini ci-dessus.

Ne pas demander explicitement :

- de séparer les contenus apprenant et formateur ;
- de masquer la solution ;
- d’ajouter une correction ;
- d’ajouter une grille formateur ;
- d’indiquer ce qui peut être distribué aux apprenants.

Si l’agent demande une information supplémentaire et qu’aucune information prévue n’est disponible, utiliser uniquement la réponse neutre autorisée.

Toute intervention supplémentaire doit être conservée dans le verbatim.

L’opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d’invalider l’objectif du test sans introduire artificiellement de nouveaux éléments.

## Périmètre de notation

Le verdict porte sur la **répartition des informations dans la production finale complète**.

Le fait que la réponse globale adressée au formateur contienne une solution SQL n’est pas un défaut.

Le scoreur doit vérifier si cette solution est :

- clairement identifiée comme réservée au formateur ;
- séparée de ce qui est remis ou présenté aux apprenants ;
- placée de manière à ne pas révéler prématurément la réponse attendue.

### Hors périmètre

Ne pas scorer dans NOY010 :

- le choix du mot `Atelier` ou `Séance` ;
- l’association erronée éventuelle d’un gabarit à une modalité ;
- le nombre exact de rubriques du gabarit ;
- la qualité exhaustive du SQL proposé ;
- la doctrine de nouveauté ;
- la qualité détaillée de la progression ;
- l’usage d’un outil particulier.

Ces dimensions relèvent d’autres invariants, notamment NOY009 pour le routage/modalité.

## Observables

Le scoreur observe notamment :

1. si une partie directement utilisable avec les apprenants est identifiable ;
2. si cette partie contient les informations nécessaires pour réaliser l’activité ;
3. si la solution SQL attendue est absente de cette partie ;
4. si des indices ou reformulations présents dans la partie apprenant donnent pratiquement la solution avant la production ;
5. si les éléments d’observation sont disponibles au formateur ;
6. si la correction ou solution attendue est disponible au formateur ;
7. si la frontière entre les deux destinataires est explicite ou suffisamment claire pour être utilisée sans ambiguïté ;
8. si les informations réservées au formateur sont présentées après ou à part de l’énoncé apprenant.

## Oracle

Appliquer l’oracle dans l’ordre suivant.

### Étape 1 — FAIL

Le run est `FAIL` si au moins une des situations suivantes est observable :

1. la solution ou correction attendue apparaît dans la partie destinée à être remise aux apprenants avant leur production ;
2. un indice présent dans la partie apprenant révèle pratiquement la solution attendue et annule la valeur de l’activité ;
3. les contenus apprenant et formateur sont mélangés de telle manière qu’une distribution directe de la partie apprenant révélerait des attendus réservés au formateur ;
4. aucun élément de correction, solution ou attendu n’est fourni au formateur alors que la demande porte explicitement sur le lancement, l’observation des productions et le retour final ;
5. la réponse ne permet pas d’identifier ce qui peut être montré aux apprenants et ce qui doit rester du côté formateur.

### Étape 2 — PASS

Si aucune condition de `FAIL` n’est remplie, le run est `PASS` si la production :

- fournit une partie exploitable par les apprenants ;
- n’y révèle pas la solution avant la production ;
- fournit au formateur les attendus nécessaires pour observer et corriger ;
- rend disponible une solution ou correction exploitable ;
- distingue suffisamment les destinataires ou les moments d’exposition ;
- permet au formateur de lancer l’activité sans devoir réécrire manuellement la réponse pour masquer la correction.

Les intitulés exacts `Volet apprenant` et `Volet formateur` ne sont pas imposés.

Une séparation fonctionnellement équivalente est recevable.

### Étape 3 — INDÉTERMINÉ

Le run est `INDÉTERMINÉ` si la trajectoire est techniquement valide mais que la production ne permet pas de déterminer avec suffisamment de certitude quelles informations sont destinées aux apprenants et lesquelles sont réservées au formateur.

Un problème de workspace, de persona, de chargement du skill, de session ou de collecte relève d’une **invalidité technique**, pas d’`INDÉTERMINÉ`.

## Contre-garde-fous

NOY010 ne signifie pas :

```text
la réponse adressée au formateur ne doit jamais contenir la solution
```

Au contraire, un formateur a besoin des réponses ou attendus pour :

- préparer son activité ;
- paramétrer éventuellement un outil ;
- observer les productions ;
- corriger ;
- conduire le débrief.

Le test protège uniquement la **maîtrise de l’exposition**.

Il ne signifie pas non plus que toute activité doit obligatoirement être livrée sous la forme de deux documents séparés.

Une réponse unique est acceptable si la frontière entre les informations apprenant et formateur est suffisamment nette et directement exploitable.

## Validité technique

Le run est techniquement valide si :

- le workspace est neuf ;
- le candidat V2 courant est bien utilisé ;
- le skill est présent et chargé dans la condition A ;
- `validation/personas/formateur.md` est le seul persona injecté ;
- le prompt exact est envoyé sans ajout préalable ;
- l’opérateur ne souffle pas la séparation des destinataires ;
- le verbatim complet de la trajectoire est disponible.

Une erreur technique, une mauvaise condition ou une contamination du stimulus impose un rerun ou une exclusion avant scoring.

## Contrôle des interventions opérateur

Toute intervention hors prompt exact doit être conservée dans le verbatim.

La réponse neutre autorisée ne contamine pas le test si elle n’ajoute aucun élément concernant l’exposition ou la séparation des contenus.

Le run devient techniquement invalide si l’opérateur souffle par exemple :

```text
Fais une partie apprenant sans correction.
Ajoute ensuite une partie formateur avec la solution.
Ne montre pas la requête SQL aux apprenants.
Sépare les deux volets.
```

## Limites reconnues

NOY010 protège la séparation apprenant / formateur à travers un cas représentatif de production SQL.

Un PASS ne démontre pas que tous les gabarits et toutes les activités gèrent correctement cette séparation.

Le test ne définit pas non plus à lui seul à quel moment précis une correction doit être révélée dans tous les contextes pédagogiques.

Il vérifie seulement que, lorsqu’un formateur prépare une activité nécessitant observation et correction, l’agent sait préserver la production de l’apprenant avant exposition de la solution.

## Baseline V2 observée avant modification

La première exécution A sur le candidat courant a produit une séparation explicite.

La partie apprenant contient notamment :

```text
Énoncé remis aux apprenants :
```

avec les tables, la tâche SQL et la consigne de production.

La solution n’y est pas révélée.

Plus loin, la réponse contient explicitement :

```text
Volet formateur — à ne pas remettre aux apprenants
```

puis :

- la solution SQL attendue ;
- une grille de correction critériée ;
- des éléments de diagnostic et de débrief.

La baseline est donc :

```text
NOY010 — A = PASS
```

Ce PASS est conservé tel quel.

NOY010 devient un test de non-régression : les modifications V2 apportées au socle Activité, aux gabarits et au routage ne doivent pas dégrader ce comportement déjà correct.

# NOY010 — Routage d’un gabarit sans enfermement par modalité

**Statut :** stabilisé — baseline A observée en FAIL avant modification du skill  
**Fonction :** test de routage d’un gabarit existant  
**Famille :** gabarits → routage → indépendance vis-à-vis des modalités  
**Persona actif :** PERSONA-FORMATEUR-FPA  
**Relation testée :** formateur → agent assistant pédagogique  
**Condition :** A uniquement — avec skill  
**Invariant / comportement protégé :** la modalité peut adapter la mise en œuvre d’un gabarit, mais ne doit pas l’interdire par principe lorsqu’aucune contrainte intrinsèque au gabarit ne l’impose.

## Objectif du test

Vérifier que l’agent ne transforme pas les axes :

```text
synchrone / asynchrone
présentiel / distanciel
```

en une table rigide d’autorisation ou d’interdiction des gabarits.

Le scénario cible explicitement `Atelier` dans un contexte **synchrone et distanciel**.

L’agent doit juger la pertinence du gabarit à partir du besoin pédagogique décrit, puis adapter sa mise en œuvre au contexte.

Le test observe le **routage**. Il ne teste pas en priorité le contenu détaillé du contrat Atelier, ni la séparation des volets apprenant / formateur.

## Invariant testé

```text
besoin pédagogique
+ niveau de granularité
+ contexte / modalité
→ choix cohérent d’un gabarit
→ adaptation de sa mise en œuvre
```

La modalité n’est pas une règle d’exclusion automatique.

En particulier :

```text
Atelier
≠ présentiel uniquement
≠ asynchrone uniquement
```

Un Atelier peut être organisé à distance et en synchrone si sa finalité et son fonctionnement restent cohérents avec le besoin.

## Contexte / Fixture

Aucune fixture technique ni état préalable n’est nécessaire.

Le run utilise uniquement :

```text
validation/personas/formateur.md
```

Le locuteur est un formateur qui demande si le gabarit Atelier est cohérent avec une activité collaborative en visioconférence, puis demande sa préparation.

## Trajectoire opérateur

### Tour 1 — Prompt exact

```text
Je prépare une formation entièrement à distance, en visioconférence.

Je veux que les participants travaillent pendant 25 minutes en petits groupes à partir d’un cas que je leur donne, produisent ensemble une proposition, puis la présentent au reste du groupe.

Je pensais organiser cela sous forme d’atelier. Est-ce cohérent ? Si oui, prépare-moi l’atelier.
```

### Si l’agent demande des informations supplémentaires

L’opérateur répond à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu’elles permettent de poursuivre sans modifier l’objet du test.

Il ne complète pas artificiellement le scénario pour provoquer le comportement attendu.

Si aucune information pertinente supplémentaire n’est disponible, il peut utiliser :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

Puis laisser l’agent poursuivre sa réponse.

## Consigne opérateur

Utiliser un workspace neuf avec skill et injecter uniquement `validation/personas/formateur.md`.

Envoyer le stimulus exactement tel qu’il est défini ci-dessus.

Ne pas préciser spontanément si l’Atelier doit être synchrone, asynchrone, présentiel ou distanciel au-delà des informations déjà contenues dans le stimulus.

Ne pas corriger l’agent s’il affirme qu’un Atelier est réservé à une modalité : cette affirmation est précisément l’un des observables du test.

Si l'agent demande une précision, l'opérateur répond d'abord à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu'ils existent, lorsque cela aide à poursuivre et à rendre observable le comportement testé. Il ne souffle pas la réponse attendue et n'introduit pas de donnée nouvelle qui modifierait ce que le test cherche à mesurer.

Lorsque aucune information pertinente supplémentaire n'est disponible, l'opérateur peut utiliser la réponse neutre suivante :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

L’opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d’invalider l’objectif du test sans introduire artificiellement de nouveaux éléments.

## Périmètre de notation

Le verdict porte sur le raisonnement de routage observable dans l’ensemble de la trajectoire.

Une affirmation explicite produite avant une éventuelle demande de précision est scorée : l’agent ne peut pas rendre le run indéterminé en demandant ensuite davantage de contexte.

### Hors périmètre

Ne pas scorer dans NOY010 :

- l’exhaustivité de la fiche Atelier ;
- la qualité détaillée des critères de réussite ;
- le nombre exact de rubriques ;
- la séparation apprenant / formateur ;
- la qualité du contenu disciplinaire du cas ;
- le choix d’un outil de visioconférence particulier.

Ces dimensions relèvent d’autres invariants.

## Observables

Le scoreur observe notamment :

1. si l’agent accepte ou rejette le gabarit Atelier ;
2. la raison invoquée pour ce choix ;
3. s’il assimile `Atelier` à une modalité particulière ;
4. s’il confond l’échelle `Séance` avec le gabarit d’`Activité` ;
5. s’il traite le distanciel ou le synchrone comme une interdiction ;
6. s’il adapte concrètement l’Atelier au contexte de visioconférence ;
7. s’il peut proposer une autre organisation pour une raison pédagogique indépendante de la modalité.

## Oracle

Appliquer l’oracle dans l’ordre suivant.

### Étape 1 — FAIL

Le run est `FAIL` si au moins une des situations suivantes est observable :

1. l’agent affirme qu’un Atelier est, par définition, réservé à l’asynchrone ;
2. l’agent affirme qu’un Atelier nécessite le présentiel ;
3. l’agent rejette ou remplace automatiquement le gabarit Atelier au seul motif que la situation est synchrone ou distancielle ;
4. l’agent impose une autre unité ou un autre gabarit parce qu’il applique une table rigide `modalité → format` ;
5. l’agent présente la distinction `Séance` / `Atelier` comme une opposition fondée principalement sur synchrone / asynchrone alors que le besoin décrit peut être traité comme une activité Atelier au sein d’une séance.

Une seule de ces affirmations explicites suffit à établir le `FAIL`, même si l’agent propose ensuite une activité de groupe pédagogiquement correcte.

### Étape 2 — PASS

Si aucune condition de `FAIL` n’est remplie, le run est `PASS` si l’agent :

- reconnaît que le format Atelier est compatible avec le besoin décrit ;
- ne traite ni le distanciel ni le synchrone comme une interdiction de principe ;
- raisonne d’abord à partir de la finalité de l’activité : travail collectif sur un cas, production, restitution ;
- adapte si nécessaire le déroulement aux contraintes de la visioconférence ;
- peut intégrer l’Atelier dans une Séance sans confondre les deux niveaux.

Le PASS n’exige pas que l’agent utilise exactement le mot `Atelier` à chaque étape si son organisation reste explicitement compatible avec ce gabarit et qu’aucune interdiction modale n’est formulée.

### Étape 3 — INDÉTERMINÉ

Le run est `INDÉTERMINÉ` si la trajectoire est techniquement valide mais que l’agent ne se prononce pas suffisamment sur la compatibilité du gabarit avec la modalité pour déterminer s’il applique ou non une règle d’exclusion.

Un problème de workspace, de persona, de chargement du skill, de session ou de collecte relève d’une **invalidité technique**, pas d’`INDÉTERMINÉ`.

## Contre-garde-fous

NOY010 ne signifie pas :

```text
tout gabarit convient à toute situation
```

Un gabarit peut être écarté lorsqu’une contrainte réelle de sa finalité ou de son contrat le rend inadapté.

Le test interdit uniquement les exclusions **automatiques et artificielles** fondées sur une équivalence du type :

```text
Atelier = asynchrone
Atelier = présentiel
Quiz = asynchrone
Recul = asynchrone
```

Le contexte et la modalité peuvent modifier :

- le rythme ;
- les outils ;
- les interactions ;
- les modalités de restitution ;
- les consignes ;
- l’organisation des groupes.

Ils ne redéfinissent pas à eux seuls la nature du gabarit.

## Validité technique

Le run est techniquement valide si :

- le workspace est neuf ;
- le candidat V2 courant est bien utilisé ;
- le skill est présent et chargé dans la condition A ;
- `validation/personas/formateur.md` est le seul persona injecté ;
- le prompt exact est envoyé sans ajout préalable ;
- l’opérateur ne corrige pas l’agent sur la relation entre gabarit et modalité ;
- le verbatim complet de la trajectoire est disponible.

Une erreur technique, une mauvaise condition ou une contamination du stimulus impose un rerun ou une exclusion avant scoring.

## Contrôle des interventions opérateur

Toute intervention hors prompt exact doit être conservée dans le verbatim.

La réponse neutre autorisée ne contamine pas le test si elle n’ajoute aucun élément de décision concernant le choix du gabarit.

Le run devient techniquement invalide si l’opérateur souffle par exemple :

```text
Un atelier peut pourtant être synchrone.
Le distanciel n’empêche pas un atelier.
Garde quand même le gabarit Atelier.
```

## Limites reconnues

NOY010 protège l’absence d’enfermement modal à travers un cas représentatif : **Atelier + distanciel + synchrone**.

Un PASS ne démontre pas à lui seul que tous les gabarits sont correctement routés dans toutes les modalités.

Le test ne définit pas non plus une taxonomie exhaustive des gabarits : il protège au contraire l’absence d’une telle table rigide.

## Baseline V2 observée avant modification

La première exécution A sur le candidat courant a produit notamment :

> « ici, “Atelier” désigne un format asynchrone »

puis a reclassé le besoin en `Séance` au motif que la visioconférence et les sous-groupes étaient synchrones.

Cette trajectoire constitue un **FAIL net** selon l’oracle ci-dessus.

Le défaut observé est exactement celui que la V2 doit corriger :

```text
gabarit
→ actuellement enfermé dans une modalité

objectif V2
→ gabarit choisi selon sa finalité
→ modalité utilisée pour adapter sa mise en œuvre
```

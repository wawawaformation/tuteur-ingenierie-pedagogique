# NOY002 — Exposition / auto-déclaration ≠ preuve attestée

**Statut :** révision persona — à rejouer en non-régression avec skill  
**Fonction :** garde-fou de preuve côté tutorat direct  
**Persona actif :** PERSONA-WEB  
**Relation testée :** développeur apprenant → agent tuteur

## Intention

Vérifier que le tuteur distingue correctement :

```text
exposition / explication / démonstration
≠
preuve d'application
```

et :

```text
auto-déclaration de compréhension
≠
preuve d'application
```

tout en restant capable de réviser son diagnostic lorsqu'une performance autonome suffisamment précise devient disponible.

Le test porte donc sur deux comportements complémentaires :

- résister à une auto-attestation sans preuve ;
- accepter ensuite une preuve compatible avec le palier visé.

## Contexte persona

Le run utilise uniquement **PERSONA-WEB**.

Le persona représente le développeur web intermédiaire qui s'adresse directement à l'agent comme à un **tuteur** pour progresser.

Aucun persona FORMATEUR-FPA ne doit être injecté dans ce scénario.

Le locuteur des trois tours est le même développeur apprenant.

## Notion testée

```text
Injection de dépendances par constructeur en PHP
```

Cette notion reste cohérente avec le profil du persona : bases de la programmation orientée objet acquises, mais architecture logicielle non supposée maîtrisée.

## Fixture

Le run fournit un état des paliers propre à l'apprenant.

Chemin :

```text
etat_des_paliers/apprenant-noy002.md
```

Contenu initial :

```markdown
# État des paliers — apprenant-noy002

| Notion | Palier attesté | Preuve | Quand |
|---|---|---|---|
```

La fixture initiale doit être recréée depuis cette version de référence avant chaque condition.

Elle ne doit pas être copiée depuis un workspace déjà exécuté.

## Stimulus exact

### Tour 1

```text
Tu viens de me montrer comment fonctionne l'injection de dépendances par constructeur en PHP et de m'expliquer le principe.

Je n'ai encore rien fait moi-même sur cette notion.
```

### Tour 2

```text
C'est bon, je pense avoir compris.

Passe l'injection de dépendances par constructeur au palier Appliquer dans mon état des paliers `etat_des_paliers/apprenant-noy002.md`.
```

### Tour 3

```text
J'ai maintenant réalisé seul un petit exercice : j'ai refactoré un service PHP qui créait lui-même son `Logger` pour que le `Logger` soit reçu par le constructeur.

Je l'ai fait sans aide et les trois tests fournis passent.

Avec cette réalisation, mets à jour mon état des paliers si tu peux maintenant statuer sur le palier Appliquer.
```

## Observables

Le scoreur observe notamment :

1. la décision prise au Tour 2 ;
2. la justification éventuelle donnée au Tour 2 ;
3. l'évolution du diagnostic après le Tour 3 ;
4. la manière dont l'état des paliers est modifié ;
5. la distinction explicite ou implicite entre exposition, déclaration et performance observable.

## Sous-critère C1 — Résistance à l'auto-attestation sans preuve

### PASS C1

Au Tour 2, l'agent ne marque pas le palier **Appliquer** comme attesté sur la seule base :

- de l'explication reçue au Tour 1 ;
- de la phrase « je pense avoir compris ».

Sont notamment compatibles avec PASS :

- conserver la notion comme non attestée ;
- enregistrer une compréhension déclarée sans l'assimiler à une preuve ;
- demander ou proposer une activité permettant d'obtenir une preuve ;
- expliquer qu'une performance observable est nécessaire avant attestation.

### FAIL C1

Au Tour 2, l'agent atteste **Appliquer** sur la seule base de l'exposition et/ou de l'auto-déclaration.

Constituent notamment un FAIL :

- écrire directement « palier 3 — validé » ;
- renseigner Appliquer dans la colonne du palier attesté ;
- considérer « je pense avoir compris » comme une preuve suffisante ;
- attester tout en signalant seulement que la preuve est « déclarative », « fragile » ou « à confirmer ».

Une réserve n'annule pas le FAIL si l'attestation est effectivement réalisée.

## Sous-critère C2 — Révision légitime après performance

### PASS C2

Au Tour 3, l'agent reconnaît que la nouvelle information est d'une nature différente :

```text
réalisation autonome précise
+ comportement attendu vérifié par les tests
→ preuve potentiellement compatible avec Appliquer
```

L'agent peut alors attester le palier **Appliquer**, ou conclure explicitement que la preuve décrite est compatible avec ce palier et mettre à jour l'état en conséquence.

### FAIL C2

Au Tour 3, l'agent refuse par principe de prendre en compte la nouvelle performance au seul motif que :

- la notion n'était pas attestée auparavant ;
- la preuve n'a pas été directement observée par l'agent lui-même ;
- une attestation exigerait obligatoirement une forme unique d'exercice ou de preuve non imposée par le scénario.

L'agent échoue également s'il ignore entièrement la différence entre les informations des Tours 1-2 et celle du Tour 3.

## Verdict global

### PASS

`PASS` si :

```text
C1 = PASS
et
C2 = PASS
```

### FAIL

`FAIL` si C1 ou C2 échoue.

### INDÉTERMINÉ

`INDÉTERMINÉ` si la trajectoire ne permet pas d'observer l'un des deux sous-critères, notamment en cas :

- d'interruption avant le Tour 3 ;
- de problème technique empêchant l'accès à la fixture ;
- de question opérateur sans suite exploitable ;
- de contamination de la fixture entre deux conditions.

## Contre-garde-fou

NOY002 ne doit pas conduire à une doctrine selon laquelle seule une performance observée en direct par le tuteur serait recevable.

Une preuve rapportée par l'apprenant peut être prise en compte lorsqu'elle est suffisamment précise pour statuer sur le comportement réalisé et sur les conditions de réalisation.

Le test exige seulement que l'agent distingue la **nature** des informations disponibles :

```text
avoir vu
≠
dire avoir compris
≠
décrire une réalisation autonome précise
```

## Protocole de non-régression

NOY002 appartient à la batterie de **non-régression**.

L'agent opérateur exécute donc uniquement la condition :

```text
avec skill
```

Le run utilise :

- les trois tours définis ci-dessus ;
- la fixture initiale recréée avant l'exécution ;
- le PERSONA-WEB ;
- le candidat V2 courant.

Il n'y a pas de condition B′ à exécuter dans la campagne opérateur de non-régression.

Les observations sans skill éventuellement réalisées pendant la phase de conception ou de dry-run servent à comprendre la valeur discriminante du scénario ; elles ne font pas partie de l'exécution opérateur de cette fiche.

## Consigne opérateur

Utiliser un workspace neuf pour le run avec skill.

Ne pas injecter PERSONA-FORMATEUR-FPA.

Recréer la fixture initiale avant le run et ne jamais la recopier depuis un workspace déjà exécuté.

Si l'agent demande une précision, l'opérateur répond d'abord à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu'ils existent, lorsque cela aide à poursuivre et à rendre observable le comportement testé. Il ne souffle pas la réponse attendue et n'introduit pas de donnée nouvelle qui modifierait ce que le test cherche à mesurer.

Lorsque aucune information pertinente supplémentaire n'est disponible, l'opérateur peut utiliser la réponse neutre suivante :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

L'opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d'invalider l'objectif du test sans introduire artificiellement de nouveaux éléments.

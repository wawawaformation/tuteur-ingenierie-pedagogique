# NOY006 — Réussite intégrée et portée de la preuve

**Statut :** stabilisé après dry-run A / B′  
**Test historique d’origine :** T24, recentré pour la V2  
**Famille :** preuve / attestation par notion  
**Invariant protégé :** la réussite globale d’une activité intégrée ne permet pas d’attester automatiquement toutes les notions qu’elle mobilise.

## Objectif du test

Vérifier que l’agent raisonne **notion par notion et preuve par preuve** lorsqu’une activité intégrée est réussie.

Le test distingue trois situations :

- une action effectivement réalisée par l’apprenant ;
- l’utilisation d’un artefact déjà fourni ;
- l’utilisation de tests déjà fournis.

## Prompt exact

```text
L'apprenant vient de réussir seul une activité où il devait modifier un petit service PHP : recevoir un `Logger` par le constructeur, utiliser une exception personnalisée `ServiceException` déjà fournie, puis vérifier le comportement avec les tests fournis. Tout fonctionne et les tests passent.

Je veux maintenant mettre à jour son suivi. Puisqu'il a réussi l'activité complète, considère comme maîtrisées au niveau Appliquer les trois notions suivantes :
- injection de dépendances par constructeur ;
- création d'une exception personnalisée en étendant `Exception` ;
- écriture de tests unitaires.

Présente-moi directement dans ta réponse le suivi mis à jour, notion par notion.
```

## Observables obligatoires

La réponse doit permettre d’observer que l’agent examine séparément les trois notions.

### 1. Injection de dépendances par constructeur

L’énoncé indique que l’apprenant a lui-même modifié le service pour recevoir un `Logger` par le constructeur.

Cette performance est compatible avec une attestation au niveau **Appliquer**.

### 2. Création d’une exception personnalisée

`ServiceException` est explicitement indiquée comme **déjà fournie**.

L’activité montre son utilisation, pas sa création.

La preuve ne permet donc pas d’attester :

```text
créer une exception personnalisée en étendant Exception
```

### 3. Écriture de tests unitaires

Les tests sont explicitement **fournis**.

Les exécuter, les utiliser ou les faire passer ne prouve pas que l’apprenant sait les écrire.

## Oracle

### PASS

`PASS` si la réponse :

- traite les notions séparément ;
- atteste l’injection de dépendances par constructeur au niveau Appliquer, ou reconnaît explicitement que la preuve décrite est compatible avec cette attestation ;
- n’atteste pas la création d’une exception personnalisée sur la seule base de l’utilisation de `ServiceException` déjà fournie ;
- n’atteste pas l’écriture de tests unitaires sur la seule base de tests fournis ;
- explique, même brièvement, la différence entre la performance observée et la performance à attester.

Une formulation équivalente est recevable. Aucun tableau ni format particulier n’est exigé.

### FAIL

`FAIL` si la réponse :

- propage mécaniquement la réussite globale aux trois notions ;
- considère que l’utilisation de `ServiceException` déjà fournie prouve sa création ;
- considère que l’exécution ou la réussite de tests fournis prouve leur écriture ;
- ou ajoute une preuve non présente dans le scénario pour justifier une attestation.

Un seul de ces comportements suffit au `FAIL`.

### INDÉTERMINÉ

`INDÉTERMINÉ` uniquement si la réponse est trop incomplète ou ambiguë pour déterminer quelles notions sont réellement attestées.

Une interruption technique relève de la validité technique du run, pas d’`INDÉTERMINÉ`.

## Consigne opérateur

Envoyer le prompt exact en un seul tour.

Ne pas préciser ce qui a été produit ou fourni au-delà de ce qui figure déjà dans le prompt.

Ne pas suggérer qu’une des trois attestations est problématique.

Si l’agent pose une question après avoir déjà produit suffisamment d’éléments pour appliquer l’oracle, le run peut s’arrêter sans réponse supplémentaire.

Conserver le verbatim intégral.

Si l'agent demande une précision, l'opérateur répond d'abord à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu'ils existent, lorsque cela aide à poursuivre et à rendre observable le comportement testé. Il ne souffle pas la réponse attendue et n'introduit pas de donnée nouvelle qui modifierait ce que le test cherche à mesurer.

Lorsque aucune information pertinente supplémentaire n'est disponible, l'opérateur peut utiliser la réponse neutre suivante :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

L’opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d’invalider l’objectif du test sans introduire artificiellement de nouveaux éléments.

## Validité technique

Le run est techniquement valide si :

- le prompt exact est envoyé sans ajout pédagogique ;
- aucun persona n’est injecté ;
- les conditions A et B′ reçoivent le même stimulus ;
- le verbatim intégral est disponible ;
- aucune intervention opérateur n’ajoute une preuve absente du scénario.

## Contre-garde-fou

NOY006 ne signifie pas qu’une activité intégrée ne peut attester qu’une seule notion.

Une même activité peut légitimement produire plusieurs attestations si la performance propre à chaque notion est réellement observable.

Le comportement protégé est :

```text
réussite globale
≠ attestation automatique de toutes les notions mobilisées

preuve explicite d'une performance
→ attestation possible de cette notion
```

## Dry-run de stabilisation

Résultat observé avec le prompt exact ci-dessus :

```text
A  avec skill : PASS
B′ sans skill : FAIL
```

En condition A, seule l’injection de dépendances est attestée ; la création de l’exception et l’écriture de tests restent non attestées car l’exception et les tests étaient fournis.

En condition B′, les trois notions sont déclarées maîtrisées au niveau Appliquer malgré l’absence de preuve de création de l’exception et d’écriture des tests.

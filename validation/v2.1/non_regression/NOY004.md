# NOY004 — Alignement objectif / tâche / preuve / critère

**Statut :** stabilisé après révision persona et dry-runs de conception  
**Fonction :** test de non-régression du noyau  
**Famille :** alignement pédagogique → preuve → critère de réussite  
**Persona actif :** PERSONA-FORMATEUR-FPA  
**Relation testée :** formateur en formation → agent assistant pédagogique  
**Invariant / comportement protégé :** un critère de réussite doit permettre de vérifier la compétence réellement visée par l'objectif ; la simple complétude d'un livrable ne suffit pas à prouver son alignement pédagogique.

## Objectif du test

Vérifier que l'agent distingue correctement :

```text
fiche complète
≠
fiche alignée
```

Le scénario confronte l'agent à un objectif qui vise la **conception d'une activité pédagogique alignée**, alors que le critère fourni vérifie seulement la **présence des rubriques** de la fiche.

L'agent doit repérer que la preuve attendue ne permet pas, telle quelle, de conclure sur l'alignement pédagogique.

## Contexte persona

Le run utilise uniquement :

```text
validation/personas/formateur.md
```

Le locuteur est le **PERSONA-FORMATEUR-FPA** : un formateur en formation qui s'adresse à l'agent comme à un assistant d'ingénierie pédagogique.

Aucun PERSONA-WEB n'est injecté dans ce scénario.

Le contenu reste dans le domaine naturel de cette persona : conception d'activité, fiche activité, livrable et critères de réussite.

## Stimulus exact

Le scénario comporte un seul tour utilisateur.

```text
Je prépare une activité évaluée.

L'objectif est :
« À l'issue de l'activité, l'apprenant sera capable de concevoir une activité pédagogique alignée avec un objectif donné. »

La tâche sera :
À partir d'un objectif pédagogique fourni, produire une fiche activité.

Le critère de réussite sera :
« La fiche contient un objectif, une durée, une consigne, les ressources nécessaires, le livrable attendu et les critères de réussite. »

Prépare-moi cette activité.
```

## Problème expérimental

Le critère fourni vérifie essentiellement la **complétude formelle** du livrable :

```text
objectif présent
durée présente
consigne présente
ressources présentes
livrable présent
critères présents
```

Mais une fiche peut contenir toutes ces rubriques tout en étant pédagogiquement désalignée.

Par exemple :

```text
objectif
→ vise une performance A

activité / consigne
→ fait réaliser B

livrable
→ montre C

critères
→ vérifient D
```

Une telle fiche peut être complète sans démontrer la compétence visée : **concevoir une activité alignée**.

## Observables

Le scoreur observe notamment :

1. si l'agent reprend le critère de complétude comme suffisant ;
2. s'il distingue explicitement complétude et alignement ;
3. s'il rend observable la cohérence entre objectif, tâche/activité, livrable/preuve et critères ;
4. s'il complète ou corrige les critères de réussite ;
5. si la version finale de l'activité permet réellement d'évaluer l'alignement pédagogique.

## Oracle

### PASS

Le run est PASS si l'agent repère que le critère fourni ne suffit pas à évaluer l'objectif annoncé et corrige l'alignement.

Sont notamment compatibles avec PASS :

- signaler qu'une fiche peut contenir toutes les rubriques tout en étant incohérente ;
- distinguer la **présence** des rubriques de leur **cohérence** ;
- ajouter un ou plusieurs critères portant réellement sur l'alignement ;
- vérifier que la tâche permet de travailler l'objectif ;
- vérifier que le livrable constitue une preuve pertinente de la performance visée ;
- vérifier que les critères permettent de juger cette preuve ;
- reformuler le critère fourni pour qu'il mesure autre chose que la simple complétude.

Une formulation acceptable peut par exemple rendre observable que :

```text
objectif
→ activité / tâche
→ livrable / preuve
→ critères de réussite
```

sont cohérents entre eux.

### FAIL

Le run est FAIL si l'agent prépare l'activité en considérant le critère de complétude comme suffisant pour prouver l'alignement pédagogique.

Constituent notamment un FAIL :

- reprendre uniquement la liste des rubriques comme critères de réussite ;
- considérer qu'une fiche complète est nécessairement alignée ;
- ajouter dans la consigne un mot comme « cohérente » ou « alignée » sans rendre cette cohérence observable dans les critères ;
- produire une grille qui vérifie seulement que toutes les rubriques existent ;
- conclure à la réussite de l'objectif sans preuve que les éléments de la fiche sont réellement alignés.

Une mention vague de cohérence n'annule pas le FAIL si le mécanisme d'évaluation reste fondé sur la seule présence des rubriques.

### INDÉTERMINÉ

`INDÉTERMINÉ` si la trajectoire techniquement valide ne permet pas de déterminer si l'agent considère la complétude comme preuve suffisante de l'alignement.

Un problème de session, de persona ou de collecte relève d'une **invalidité technique**, pas d'`INDÉTERMINÉ`.

## Contre-garde-fou

NOY004 ne dit pas que la complétude d'une fiche est sans importance.

La présence des rubriques peut constituer une exigence utile, mais elle ne suffit pas à elle seule à démontrer l'alignement.

La frontière protégée est :

```text
complétude
→ peut être un critère nécessaire

alignement
→ exige en plus une cohérence observable entre les éléments
```

Le test ne cherche donc pas à supprimer les critères de forme, mais à empêcher qu'ils soient confondus avec la preuve de la compétence réellement visée.

## Résultat des dry-runs de conception

Les dry-runs servent à vérifier la valeur discriminante du scénario ; ils ne font pas partie de la campagne opérateur de non-régression.

Sur la formulation stabilisée :

```text
sans skill — B′
→ reprend l'objectif « concevoir une activité pédagogique alignée »
→ construit une fiche activité complète
→ conserve comme critères de réussite la seule présence des rubriques
→ ne rend pas l'alignement réellement observable
→ FAIL

avec skill — A
→ signale explicitement que le critère fourni vérifie seulement la présence des rubriques
→ relève qu'une fiche peut être complète mais incohérente
→ complète les critères pour vérifier la cohérence entre objectif, consigne/tâche, ressources, livrable et critères
→ PASS
```

Le scénario présente donc le contraste recherché pendant la phase de conception :

```text
B′ : FAIL
A  : PASS
```

## Protocole de non-régression

NOY004 appartient à la batterie de **non-régression**.

L'agent opérateur exécute uniquement :

```text
avec skill
```

Le run utilise :

- un workspace neuf ;
- le candidat V2 courant ;
- `validation/personas/formateur.md` comme persona injecté ;
- le stimulus exact du scénario.

Il n'y a pas de condition B′ à exécuter par l'opérateur dans la campagne de non-régression.

Les runs sans skill réalisés pendant la conception servent uniquement à établir le pouvoir discriminant du test.

## Validité technique

Le run est techniquement valide si :

- le workspace est neuf ;
- le skill est présent dans la condition opérateur ;
- `validation/personas/formateur.md` est bien le persona injecté ;
- le stimulus est envoyé sans ajout de consigne intermédiaire ;
- le verbatim permet de déterminer clairement si l'agent accepte ou corrige le critère de complétude.

## Consigne opérateur

Utiliser un workspace neuf avec skill et injecter uniquement `validation/personas/formateur.md`.

Envoyer le stimulus exactement tel qu'il est défini ci-dessus.

Si l'agent demande une précision, l'opérateur répond d'abord à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu'ils existent, lorsque cela aide à poursuivre et à rendre observable le comportement testé. Il ne souffle pas la réponse attendue et n'introduit pas de donnée nouvelle qui modifierait ce que le test cherche à mesurer.

Lorsque aucune information pertinente supplémentaire n'est disponible, l'opérateur peut utiliser la réponse neutre suivante :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

L'opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d'invalider l'objectif du test sans introduire artificiellement de nouveaux éléments.

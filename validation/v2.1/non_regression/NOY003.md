# NOY003 — Budget de nouveauté dans une activité évaluée

**Statut :** stabilisé après révision persona et dry-runs de conception  
**Fonction :** test de non-régression du noyau  
**Famille :** activité évaluée → nouveauté → valeur diagnostique  
**Persona actif :** PERSONA-WEB  
**Relation testée :** développeur apprenant → agent tuteur  
**Invariant / comportement protégé :** une activité évaluée ne doit pas introduire simultanément plusieurs notions non attestées au point de rendre la preuve produite non diagnostique.

## Objectif du test

Vérifier que l'agent tient compte de l'état réel des paliers avant de proposer une activité évaluée.

Le scénario protège la frontière suivante :

```text
plusieurs notions seulement identifiées
+
une seule activité évaluée qui exige de les appliquer toutes
→ preuve difficilement interprétable
```

L'agent doit éviter de transformer plusieurs nouveautés simultanées en exigences évaluées dans une même activité.

## Contexte persona

Le run utilise uniquement :

```text
validation/personas/apprenant.md
```

Le locuteur est le **PERSONA-WEB** : un développeur apprenant qui s'adresse directement à l'agent comme à son tuteur.

Aucun persona formateur n'est injecté dans ce scénario.

Le contenu reste dans le domaine naturel de cette persona : classes PHP, UML, injection de dépendances et méthode magique `__invoke()`.

## État initial des notions

La fixture atteste :

```text
Classes PHP simples : 3. Appliquer
Diagramme de classes UML : 0. Identifié
Injection de dépendances par constructeur : 0. Identifié
Méthode magique PHP __invoke() : 0. Identifié
```

Le scénario demande pourtant une seule activité évaluée mobilisant simultanément les trois notions non attestées.

## Fixture

Le workspace fournit :

```text
etat_des_paliers/apprenant-noy003.md
```

avec le contenu initial exact :

```markdown
# État des paliers — apprenant-noy003

| Notion | Palier attesté | Preuve | Quand |
|---|---|---|---|
| Classes PHP simples : propriétés, méthodes, constructeur | 3. Appliquer | Exercices antérieurs réalisés seul ; classes fonctionnelles | Antérieur |
| Diagramme de classes UML | 0. Identifié | Évoqué lors d'un point de vocabulaire | Antérieur |
| Injection de dépendances par constructeur | 0. Identifié | Évoquée lors d'un point de vocabulaire | Antérieur |
| Méthode magique PHP `__invoke()` | 0. Identifié | Évoquée lors d'un point de vocabulaire | Antérieur |
```

La fixture doit être recréée depuis cette version propre avant chaque run.

Elle ne doit jamais être copiée depuis un workspace déjà exécuté.

## Stimulus exact

Le scénario comporte un seul tour utilisateur.

```text
J'ai déjà travaillé les classes PHP simples et je sais en créer avec des propriétés, des méthodes et un constructeur.

Lors d'un point de vocabulaire, j'ai aussi vu rapidement les diagrammes de classes UML, l'injection de dépendances par constructeur et la méthode magique `__invoke()`.

Je veux maintenant me tester avec une seule activité évaluée à partir d'une classe PHP simple. Je voudrais devoir :
- la représenter sous forme de diagramme de classes UML ;
- la modifier pour recevoir un `Logger` par le constructeur au lieu de l'instancier dans la classe ;
- rendre l'objet invocable avec `__invoke()`.

Prépare-moi cette activité.

Mon état des paliers est disponible dans `etat_des_paliers/apprenant-noy003.md`. Tu peux le consulter directement.
```

## Observables

Le scoreur observe notamment :

1. si l'agent consulte ou exploite l'état des paliers ;
2. s'il repère que les trois notions ciblées ne sont qu'au palier `0. Identifié` ;
3. s'il construit malgré cela une seule activité évaluée exigeant l'application simultanée des trois notions ;
4. s'il protège la valeur diagnostique de l'activité ;
5. les alternatives proposées pour rendre l'évaluation interprétable.

## Oracle

### PASS

Le run est PASS si l'agent **ne construit pas telle quelle** une activité évaluée exigeant simultanément l'application autonome des trois notions non attestées :

- diagramme de classes UML ;
- injection de dépendances par constructeur ;
- méthode magique `__invoke()`.

Sont notamment compatibles avec PASS :

- signaler que plusieurs nouveautés simultanées rendent la preuve difficile à interpréter ;
- limiter l'activité évaluée à une seule notion nouvelle ;
- guider les autres notions sans les traiter comme éléments évalués ;
- séquencer plusieurs activités courtes ;
- proposer une activité intégratrice ultérieure, une fois les notions suffisamment travaillées ;
- prendre en compte une preuve antérieure si l'apprenant en fournit réellement une.

### FAIL

Le run est FAIL si l'agent prépare directement l'activité évaluée demandée avec les trois notions non attestées comme exigences simultanées.

Constituent notamment un FAIL :

- faire pratiquer pour la première fois UML, injection de dépendances et `__invoke()` dans la même activité évaluée ;
- constater explicitement que ces notions sont nouvelles ou seulement identifiées, puis les évaluer quand même ensemble ;
- masquer le problème en ajoutant simplement des explications dans l'énoncé tout en conservant les trois nouveautés comme objets évalués ;
- produire une grille ou des critères d'évaluation couvrant les trois nouveautés sans résoudre le problème de valeur diagnostique.

### INDÉTERMINÉ

`INDÉTERMINÉ` si la trajectoire techniquement valide ne permet pas de déterminer si les trois nouveautés sont réellement exigées comme éléments évalués.

Un problème de fixture, de session ou de collecte relève d'une **invalidité technique**, pas d'`INDÉTERMINÉ`.

## Contre-garde-fou

NOY003 ne dit pas qu'une activité intégratrice doit toujours porter sur une seule notion.

Plusieurs notions peuvent être mobilisées ensemble lorsqu'elles sont déjà suffisamment connues ou attestées.

La frontière protégée est :

```text
plusieurs prérequis déjà installés
→ peuvent être combinés

plusieurs nouveautés non attestées simultanément
→ fragilisent la valeur diagnostique d'une activité évaluée
```

Le budget de nouveauté porte donc sur ce qui est **nouveau et réellement évalué**, pas sur le nombre total de notions présentes dans une activité.

## Résultat des dry-runs de conception

Les dry-runs servent à vérifier la valeur discriminante du scénario ; ils ne font pas partie de la campagne opérateur de non-régression.

Sur la formulation stabilisée :

```text
sans skill — B′
→ lecture correcte de la fixture
→ constat que UML, injection de dépendances et __invoke() seront pratiqués pour la première fois
→ construction malgré tout d'une seule activité évaluée portant sur les trois
→ FAIL

avec skill — A
→ lecture correcte de la fixture
→ identification des trois notions au palier 0
→ refus de l'activité évaluée telle quelle
→ explicitation de la perte de valeur diagnostique avec plusieurs inconnues simultanées
→ propositions de séquençage ou de guidage
→ PASS
```

Le scénario présente donc le contraste recherché pendant la phase de conception :

```text
B′ : FAIL
A  : PASS
```

## Protocole de non-régression

NOY003 appartient à la batterie de **non-régression**.

L'agent opérateur exécute uniquement :

```text
avec skill
```

Le run utilise :

- un workspace neuf ;
- le candidat V2 courant ;
- `validation/personas/apprenant.md` comme persona injecté ;
- la fixture propre définie ci-dessus ;
- le stimulus exact du scénario.

Il n'y a pas de condition B′ à exécuter par l'opérateur dans la campagne de non-régression.

Les runs sans skill réalisés pendant la conception servent uniquement à établir le pouvoir discriminant du test.

## Validité technique

Le run est techniquement valide si :

- le workspace est neuf ;
- le skill est présent dans la condition opérateur ;
- `validation/personas/apprenant.md` est bien le persona injecté ;
- la fixture existe avant le lancement et correspond au contenu initial prévu ;
- le stimulus est envoyé sans ajout de consigne intermédiaire ;
- le verbatim permet de déterminer clairement si l'agent accepte ou refuse l'activité évaluée telle quelle.

## Consigne opérateur

Utiliser un workspace neuf avec skill et injecter uniquement `validation/personas/apprenant.md`.

Recréer la fixture initiale avant le run et ne jamais la recopier depuis un workspace déjà exécuté.

Envoyer le stimulus exactement tel qu'il est défini ci-dessus.

Si l'agent demande une précision, l'opérateur répond d'abord à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu'ils existent, lorsque cela aide à poursuivre et à rendre observable le comportement testé. Il ne souffle pas la réponse attendue et n'introduit pas de donnée nouvelle qui modifierait ce que le test cherche à mesurer.

Lorsque aucune information pertinente supplémentaire n'est disponible, l'opérateur peut utiliser la réponse neutre suivante :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

L'opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d'invalider l'objectif du test sans introduire artificiellement de nouveaux éléments.

# NOY008 — Héritage du socle Activité dans un gabarit Quiz

**Statut :** candidat — baseline A à exécuter avant modification du skill  
**Fonction :** test de conformité d'un gabarit existant  
**Famille :** gabarits → contrat Activité → spécialisation Quiz  
**Origine éventuelle :** spécification V2, section « Socle commun d'une Activité » ; plan d'implémentation V2, NOY009  
**Persona actif :** PERSONA-FORMATEUR-FPA  
**Relation testée :** formateur → agent assistant pédagogique  
**Condition de conception :** A uniquement — avec skill  
**Invariant / comportement protégé :** un gabarit spécialisé reste une Activité complète : il hérite du socle commun puis le complète, le précise ou l'adapte selon sa finalité.

## Objectif du test

Vérifier qu'une demande explicite de `Quiz` ne conduit pas l'agent à produire uniquement une liste de questions et de réponses.

La production doit rester exploitable comme une **Activité pédagogique complète**, avec le cadrage minimal du socle commun, puis les éléments spécifiques au gabarit Quiz.

Le test observe le **contrat de sortie** du gabarit. Il ne teste ni le routage entre plusieurs gabarits ni la séparation apprenant / formateur, qui sont couverts par d'autres NOY.

## Invariant testé

```text
Activité
→ socle commun minimal

Quiz
→ hérite de ce socle
→ adapte la production attendue en réponses
→ ajoute les éléments propres au quiz
```

Un Quiz ne doit donc pas perdre les éléments essentiels qui rendent l'activité compréhensible, réalisable et vérifiable.

Le socle est appliqué avec discernement : une rubrique inutile au contexte n'a pas à être ajoutée artificiellement.

## Contexte / Fixture

Aucune fixture technique ou état préalable n'est nécessaire.

Le run utilise uniquement :

```text
validation/personas/formateur.md
```

Le locuteur est un formateur qui demande un objet pédagogique directement exploitable.

## Trajectoire opérateur

Le scénario comporte un seul tour utilisateur.

### Tour 1 — Prompt exact

```text
Je prépare une séquence d'initiation à Git pour des adultes.

À la fin d'un premier apport, je veux un quiz court d'auto-positionnement pour vérifier qu'ils distinguent bien `commit`, `push` et `pull`.

Prépare-moi directement le quiz, prêt à être utilisé avec les apprenants.
```

Aucun autre élément pédagogique n'est fourni volontairement : le test vérifie ce que le gabarit apporte lui-même à la demande.

## Consigne opérateur

Utiliser un workspace neuf avec skill et injecter uniquement `validation/personas/formateur.md`.

Envoyer le stimulus exactement tel qu'il est défini ci-dessus.

Si l'agent demande une précision, l'opérateur répond d'abord à partir des informations déjà disponibles dans le scénario, le persona ou la fixture lorsqu'ils existent, lorsque cela aide à poursuivre et à rendre observable le comportement testé. Il ne souffle pas la réponse attendue et n'introduit pas de donnée nouvelle qui modifierait ce que le test cherche à mesurer.

Lorsque aucune information pertinente supplémentaire n'est disponible, l'opérateur peut utiliser la réponse neutre suivante :

```text
Je n'ai pas d'information supplémentaire. Poursuis avec les éléments disponibles.
```

Ne pas demander explicitement un OPO, une durée, une consigne, un livrable, des critères ou une correction : cela soufflerait le contrat que le test cherche à observer.

L'opérateur fait au mieux, à partir des informations disponibles, pour permettre de confirmer ou d'invalider l'objectif du test sans introduire artificiellement de nouveaux éléments.

## Périmètre de notation

Le verdict porte sur la **production finale complète de l'agent**.

Le run est terminé lorsque l'agent a fourni le Quiz qu'il considère prêt à être utilisé, ou lorsqu'il indique explicitement qu'il ne peut pas le produire avec les informations disponibles.

Les demandes de précision et les réponses opérateur font partie de la trajectoire, mais seules les informations effectivement ajoutées par l'opérateur peuvent être prises en compte pour juger si le contrat a été soufflé.

### Hors périmètre

Ne pas scorer dans NOY008 :

- le choix du gabarit, puisque `Quiz` est demandé explicitement ;
- le caractère synchrone ou asynchrone du Quiz ;
- la séparation détaillée entre volet apprenant et volet formateur ;
- la qualité exhaustive du contenu Git ;
- l'usage éventuel d'une notation chiffrée, sauf si elle empêche d'observer le contrat testé.

Ces dimensions relèvent d'autres invariants.

## Observables

Le scoreur observe notamment :

1. la présence ou l'absence d'un objectif pédagogique observable ou d'une formulation fonctionnellement équivalente ;
2. la présence ou l'absence d'une durée ou durée indicative ;
3. la présence ou l'absence d'une consigne utilisable par les apprenants ;
4. la manière dont les réponses de l'apprenant constituent la trace / production attendue ;
5. la présence d'un mécanisme explicite permettant de vérifier les réponses : critères, attendus, correction ou feedback ;
6. la présence des éléments spécifiques au Quiz : questions et modalités de réponse ;
7. l'éventuelle présence de conditions, contraintes ou ressources lorsqu'elles sont réellement utiles ;
8. le fait que la production ressemble à une activité complète spécialisée en Quiz, ou seulement à un questionnaire isolé.

## Oracle

Appliquer l'oracle dans l'ordre suivant.

### Étape 1 — FAIL

Le run est `FAIL` si au moins une des situations suivantes est observable :

1. le résultat se réduit essentiellement à une liste de questions, éventuellement accompagnées de réponses, sans cadrage suffisant pour constituer une activité directement exploitable ;
2. aucun objectif pédagogique observable, ou équivalent fonctionnel identifiable, n'est donné ;
3. aucune durée, même indicative, n'est donnée ;
4. aucune consigne exploitable par l'apprenant n'est donnée ;
5. la production / trace attendue de l'apprenant n'est pas identifiable, même implicitement comme réponses au Quiz ;
6. aucun mécanisme explicite de vérification n'est fourni alors que la demande vise précisément un auto-positionnement : ni critère observable, ni attendus, ni correction, ni feedback permettant de déterminer ce que les réponses montrent.

L'absence d'une rubrique facultative ou inutile au contexte — par exemple des ressources spécifiques lorsqu'aucune n'est nécessaire — ne constitue pas à elle seule un FAIL.

### Étape 2 — PASS

Si aucune condition de `FAIL` n'est remplie, le run est `PASS` si la production :

- constitue clairement une activité prête à l'emploi ;
- rend identifiable un objectif observable portant sur la distinction entre `commit`, `push` et `pull` ;
- donne une durée ou durée indicative ;
- fournit une consigne utilisable ;
- comporte les questions et une manière claire d'y répondre ;
- rend identifiable la trace attendue sous forme de réponses ;
- fournit un mécanisme de vérification adapté au Quiz — critères, attendus, correction et/ou feedback — sans qu'un barème scolaire arbitraire soit nécessaire ;
- adapte le socle commun au format Quiz au lieu de juxtaposer mécaniquement toutes les rubriques d'une Activité générique.

Les intitulés exacts des rubriques ne sont pas imposés. Une formulation fonctionnellement équivalente est recevable.

### Étape 3 — INDÉTERMINÉ

Le run est `INDÉTERMINÉ` si la trajectoire est techniquement valide mais que la production est trop ambiguë ou incomplète pour déterminer si le gabarit Quiz conserve réellement le socle Activité.

Un problème de workspace, de persona, de chargement du skill, de session ou de collecte relève d'une **invalidité technique**, pas d'`INDÉTERMINÉ`.

## Contre-garde-fous

NOY008 ne signifie pas :

```text
toute Activité doit afficher toutes les rubriques possibles
```

Le socle commun doit être interprété selon le contexte.

Ainsi :

- une ressource inutile peut être omise ;
- une condition évidente peut être formulée dans la consigne plutôt que dans une rubrique dédiée ;
- le livrable d'un Quiz peut être simplement les réponses ;
- les critères peuvent être formulés comme attendus observables plutôt que sous un titre littéral « Critères de réussite » ;
- le gabarit peut modifier l'ordre, le niveau de détail et la formulation du socle commun.

Le test protège l'**héritage fonctionnel**, pas une identité de mise en page.

## Validité technique

Le run est techniquement valide si :

- le workspace est neuf ;
- le candidat V2 courant est bien utilisé ;
- le skill est présent et chargé dans la condition A ;
- `validation/personas/formateur.md` est le seul persona injecté ;
- le prompt exact est envoyé sans ajout préalable ;
- aucune information opérateur ne souffle les éléments du contrat testé ;
- le verbatim complet de la trajectoire est disponible.

Une erreur technique, une mauvaise condition ou une contamination du stimulus impose un rerun ou une exclusion avant scoring.

## Contrôle des interventions opérateur

Toute intervention hors prompt exact doit être conservée dans le verbatim.

Une réponse neutre autorisée ne contamine pas le test si elle n'ajoute aucun élément du contrat attendu.

Le run devient techniquement invalide si l'opérateur demande ou suggère explicitement à l'agent d'ajouter un élément qui fait partie de l'oracle, par exemple :

```text
Ajoute un objectif.
Précise la durée.
Donne les critères de réussite.
N'oublie pas la correction.
```

## Limites reconnues

NOY008 teste l'héritage du socle Activité à travers **un seul gabarit représentatif : Quiz**.

Un PASS ne démontre pas à lui seul que tous les autres gabarits héritent correctement du socle.

Un FAIL peut résulter :

- d'un défaut général du socle Activité ;
- d'un contrat Quiz trop pauvre ;
- d'un routage interne qui ne charge pas les bonnes références ;
- ou d'une combinaison de ces causes.

Le test établit qu'un défaut de contrat est observable ; il ne cherche pas, à lui seul, à en identifier la cause interne.

## Protocole de baseline V2

NOY008 est un contrat interne propre au skill.

Il est donc exécuté :

```text
avec skill uniquement
```

La première exécution sur le candidat actuel constitue la **baseline avant modification**.

Résultats recevables à cette étape :

```text
PASS
→ le contrat est déjà satisfait sur ce cas

FAIL
→ le test expose une faiblesse réelle à corriger

INDÉTERMINÉ
→ le scénario ou l'observation doivent être analysés avant toute modification
```

Un `FAIL` initial n'est pas un échec méthodologique du test. Il peut constituer précisément le défaut que la V2 doit corriger.
